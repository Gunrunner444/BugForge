# Phase 33 — Cross-contract Solidity dataflow and exploratory testing

Phase 33 extends the existing Solidity graph. It does not replace predefined
tests, static rules, fuzzing, or the reproduction and verification lifecycle.
Findings and exploratory results stay potential evidence until that lifecycle
says otherwise.

This is not full compiler semantics, not complete cross-contract symbolic
execution, not complete EVM analysis, not a UUPS or diamond certificate, not
complete DeFi verification, and not a claim of perfect sandbox isolation. A
failed generated test is not an automatic bug confirmation.

## 1. Cross-contract model

`build_project` summarizes contracts, interfaces, libraries, direct calls,
interface calls, delegatecalls, token calls, callbacks, and proxy edges
already present in the syntax graph. One scan stores that summary in a
context variable and clears it in `finally`. A later scan does not see it.

Ambiguous callees stay ambiguous. Unresolved callees stay unresolved. If the
contract or edge bound is hit, the model is incomplete, not safe.

## 2. Storage compatibility

`compare_storage_layouts` compares two storage models. Shared slot numbers are
not a collision. The same names are not identity. A variable appended after
existing storage can remain compatible. Inserting, removing, reordering,
retyping, repacking, or changing a mapping, struct, or inherited variable is
recorded as a typed change. Unknown layout stays unknown.

## 3. Proxy and implementation

A compatible proxy and implementation layout is not `sol.storage_collision`.
An incompatible layout is potential evidence. Delegatecall provenance still
distinguishes state, parameters, constants, and a Yul `sload` of a known slot.
UUPS, beacon, transparent, and diamond labels require a relationship. A word
in a string is not that relationship, and the label is not compliance.

## 4. Yul provenance

BugForge follows a short chain of `let` bindings. `let impl := sload(SLOT)`
used as a `delegatecall` target connects the target to `SLOT` when `SLOT` is
a literal or a constant. `sstore(SLOT, x)` records that `x` came from
`sload` when that binding is local and direct. Other Yul stays unknown.
This is not a Yul symbolic executor.

## 5. Exploratory testing

The model may notice a suspicious behavior, state a hypothesis, and propose a
temporary test. BugForge validates the proposal, builds an ephemeral
workspace, runs the test, returns sanitized output, and can accept a
different follow-up test. Predefined tests still run as the regression
foundation.

The intended progression is observation, hypothesis, exploratory request,
validation, execution, result analysis, follow-up or a supported hypothesis,
then the existing reproduction and verification lifecycle. A pass is not a
vulnerability. A failure is not a confirmed bug. A failure is meaningful only
when the target and hypothesis are bound, the expected behavior and oracle
are explicit, and the failure is not a tooling or safety error. Flaky results
block promotion.

## 6. Cursor and Grok

In Cursor mode BugForge does not call Grok, xAI, or any other model.
`llm_invoked` stays false. `grok-4.7` is a Cursor model label. No Grok API
key or secret is added. BugForge remains the policy, execution, evidence, and
verification authority. The model remains the planning authority inside the
tools BugForge already allows.

## 7. Safe profiles

Profiles exist for Python pytest and, only when `forge` is installed, Solidity
Foundry. Anything else is `UNSUPPORTED`. The profile chooses the command,
timeout, memory, CPU, network policy, and environment. The model cannot
override them. Foundry tests that use `ffi`, forks, RPC, environment secrets,
or filesystem cheatcodes are `BLOCKED`. The server does not accept extra
Foundry CLI flags.

## 8. Docker

Exploratory code requires Docker. If Docker is unavailable the result is
`UNAVAILABLE`. `LocalTestExecutor` is not a fallback for this path. The
repository is mounted read-only at `/bugforge-repo`. Generated tests and
artifacts use a separate writable output directory. `PYTHONPATH` is the
container path, not a host path. The shared Docker executor still uses its
default `python:3.12-slim` image, which does not include pytest or forge.
A missing interpreter is an environment error, not a reason to run on the
host. Artifact bodies are replaced with hashes, and bytes past the artifact
cap are omitted.

## 9. Budget

`security_agent_exploratory_enabled` defaults off. Limits cover the number of
tests, iterations, seconds, generated bytes, and artifact bytes. The model
cannot raise them. Live HackerOne mode cannot run this tool.

## 10. Deduplication

The candidate hash covers the repository snapshot, test code, language,
framework, target symbol, and execution profile. The same candidate returns
the previous attempt as `DUPLICATE` and is not executed again. A changed test
or snapshot is a different candidate.

## 11. Evidence

A hypothesis keeps AI provenance. The generated test is `generated_test`
provenance and is not live verification. The sandbox run is `execution`
provenance. Reproduction remains a separate step. Nothing in this path calls
`mark_verified`, changes scope, grants approval, or raises budget.

## 12. Hypothesis chaining

Every exploratory attempt is bound to the session, project, and hypothesis
BugForge already knows. A wrong id is `INVALID`. A parent attempt must be an
attempt BugForge recorded. A test for one hypothesis is not evidence for
another.

## 13. Reproducibility

Attempts record the commit, snapshot hash, test hash, profile id, and command
identity chosen by the server. Replay uses those stored inputs. A changed
repository is a different snapshot, not the same reproduction. Secrets are
not part of the metadata. The process environment is not copied into the
container.

## 14. Prompt injection

Repository source, comments, test output, and model rationale are untrusted
data. Results are redacted and wrapped as untrusted tool output. Text that
says to ignore safety, run a shell, disable the network, or mark a finding
verified does not change BugForge policy.

## 15. Known limitations

The cross-contract summary is a bounded syntactic model. It misses calls
hidden in assembly, dynamic dispatch, and most Yul. Storage comparison is not
the Solidity compiler. ERC-7201 slots are computed only for the literal,
string-keccak, and canonical formula shapes. The Python validator is a
structural reject list plus Docker, not a proof that arbitrary Python is
safe. Foundry isolation depends on Docker and the blocked cheatcode list.
External Solidity tools that are not installed stay unavailable. The default
Docker image does not bundle pytest or forge, so those exploratory profiles
need an image that already contains them. No generated test is verified
evidence by itself. A state write that happens inside a helper after the
external call is potential evidence; a write that BugForge cannot order
stays unknown.
